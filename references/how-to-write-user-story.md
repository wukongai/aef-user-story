# 如何把模糊需求写成 User Story

## 先用 3C 理解 User Story

- Card：一张简短的需求卡，写清用户、场景、目标和价值。
- Conversation：通过对话澄清、拆分、修改并确认，不把第一稿当最终答案。
- Confirmation：用可观察的验收条件确认何时算完成。

User Story 不是一句漂亮模板，而是“短卡片 + 讨论过程 + 验收共识”。

## 先分类，不要补脑

| 类别 | 直白含义 | 处理方式 |
|---|---|---|
| fact | 用户明确说了或证据支持 | 保留原意 |
| assumption | 为了继续讨论提出的猜测 | 明确标注，等待确认 |
| unknown | 现在不知道、可能影响边界 | 提问或保留未决 |
| constraint | 已确认的限制 | 记录但不冒充价值 |
| solution idea | 功能名、模型、工具或实现想法 | 留给后续方案阶段 |

如果不知道“谁、在什么场景、想完成什么、为什么有价值”，优先澄清；不影响本次边界的未知项可以保留，不要为了形式追问到底。

## Epic 和 Story 怎么区分

Epic 是较大的结果集合，常包含多个用户、多个独立结果或多个阶段。例如“做一个 AI 会议助手”通常是 Epic。

Story 是一个用户在具体场景下获得的一个结果：

> 作为〔主要用户〕，当〔具体场景〕时，我希望〔完成一个用户目标〕，从而〔获得可感知价值〕。

避免把“开发接口、设计页面、建数据表、接入模型”写成 Story；这些是后续 Task。

## 用 INVEST 检查每一条 Story

| 字母 | 判断问题 | 需要留下的证据 |
|---|---|---|
| I — Independent | 能否独立讨论、排序和交付？ | 依赖什么；能否拆开 |
| N — Negotiable | 是否描述结果，而不是锁死实现？ | 哪些实现仍可协商 |
| V — Valuable | 用户能否感知价值？ | 完成后用户得到什么 |
| E — Estimable | 信息是否足以让后续技术阶段估算？ | 已知边界和关键未知项 |
| S — Small | 是否只有一个主要用户结果，范围足够小？ | 包含和不包含什么 |
| T — Testable | 能否写出外部可观察的完成条件？ | success、failure、boundary |

`Valuable` 可以用“用户是否能走完一个有意义的垂直切片”辅助判断，但核心仍是用户获得了什么结果。INVEST 不做机械总分；任一项有风险，就说明原因并修改、拆分或保留待确认。`Estimable` 不代表在这里计算 Story Points。

## 怎么拆一个过大的需求

优先按用户结果拆：不同主要用户、不同触发场景、不同独立目标、不同业务边界。不要按前端/后端/数据库/模型团队拆。

拆完后逐条检查：删掉其他 Story，这一条是否仍能被理解和验收？如果完全没有独立价值，它可能只是实现步骤。

## 怎么写验收条件

只为已经确认的 Story 写 Given / When / Then：

- success：正常条件下执行动作，用户得到主要结果；
- failure：关键依赖或处理失败，用户得到明确、可恢复的反馈；
- boundary：权限、数量、时间、输入或状态达到边界，系统行为仍明确。

好的 Acceptance 能由外部行为观察。坏例子是“接口开发完成”“代码已合并”“测试通过”，这些是团队工作，不是用户结果。

## 修改和确认

第一稿必须允许用户确认、修改、拆分、合并、补充遗漏、暂缓和调整顺序。Story 一旦修改，相关 Acceptance 必须重新生成或复核，并再次确认。

## 常见错误

| 错误 | 改法 |
|---|---|
| 一条包含多个用户或多个结果 | 拆成多条 Story |
| 把功能名直接当价值 | 追问谁在什么场景得到什么结果 |
| 把技术方案写进目标 | 移到 solution idea 或 constraint |
| 用户没确认就继续写验收 | 停在 Story 确认门 |
| 只有成功路径 | 补 failure 和 boundary |
| Story 改了但沿用旧 Acceptance | 标记失效并重新确认 |
