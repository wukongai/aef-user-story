# User Story 塑形标准

## 目的

把不完整、混杂或方案优先的输入转成可讨论的用户价值切片，同时保留事实边界。Story Shaping 不负责决定技术实现。

## 输入分类

| 类别 | 含义 | 处理方式 |
|---|---|---|
| Fact | 用户明确提供或证据直接支持 | 保留来源，不扩大含义 |
| Assumption | 为形成候选而提出、尚未确认 | 显式标记，进入 review |
| Unknown | 会影响边界但当前不知道 | 提问或保留 open |
| Constraint | 已确认的时间、平台、政策或兼容限制 | 影响切片，但不冒充价值 |
| Solution idea | 功能名、工具、供应商、模型或技术方案 | 移出 Story 正面，留给下游 |

如果未知项会改变主要用户、触发场景、用户目标、价值或 first cut，一次询问一个信息增益最高的问题。否则继续形成候选，不为流程而追问。

## Epic 与 Story 的区别

Epic 描述一组相关用户结果或较大的产品方向。包含多个主要用户、多个独立结果、多个发布周期，或仍是“平台/系统/解决方案”时，优先判为 Epic。

Story 只保留一个主要用户、一个具体触发场景、一个用户目标和一个可感知价值。

> 作为〔主要用户〕，当〔具体场景〕时，我希望〔完成一个用户目标〕，从而〔获得可感知价值〕。

句式完整不代表事实已确认。来自推断的 actor、scenario、goal 或 value 必须标为 assumption。

## 垂直切片

垂直 Story 让用户获得一个可观察的端到端结果。“完成前端页面、建立数据库表、开发 API、接入模型、写测试、部署基础设施”是下游实现任务，不是独立 User Story。

常见垂直拆分维度：

- 主路径先于次要路径；
- 一个主要用户先于另一个用户；
- 一种输入来源先于全部来源；
- 单个对象先于批量；
- 基础权限先于复杂角色；
- 可用结果先于自动优化；
- 明确边界内的人工步骤先于自动化。

切片缩小后仍必须保留完整结果。只交付半个流程不是 first cut。

## INVEST 诊断

- Independent：能否独立讨论和排序；
- Negotiable：是否描述结果而非锁死实现；
- Valuable：用户能否感知价值；
- Estimable：未知项是否少到可以判断规模；
- Small：是否能在一个合理迭代完成；
- Testable：是否能写出外部可观察 Acceptance。

用 INVEST 找具体问题，不做机械总分：多结果则拆分；锁死方案则移到 constraint/solution idea；价值不明则询问；未知太多则保留 unknown 并停止；不可验收则改写为外部行为。

## 首个切片推荐

first cut 优先直接验证 Epic 核心价值、形成端到端结果、依赖与未知项少、可写清三类 Acceptance，并且删除后会让核心假设无法验证。

输出推荐依据、暂缓 Story、非目标和仍需用户决定的假设。推荐只进入 Story Review，不自动批准。

## User Story 评审输出顺序

1. 原始需求摘要；
2. facts / assumptions / unknowns / constraints / solution ideas；
3. Epic；
4. 候选 Story；
5. 垂直切片诊断；
6. first cut 与理由；
7. deferred Stories 和 non-goals；
8. 一个允许批准、修改、合并、拆分或更换 first cut 的确认问题。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 一句话包含多个用户 | 分成不同候选 Story |
| “第一期前端、第二期后端” | 改写为每期可体验的用户结果 |
| 只有“增加 AI 总结” | 询问谁在什么场景需要什么价值 |
| 指定模型和数据库 | 记录为方案或约束候选 |
| 把建议功能当原始需求 | 放入 assumption/deferred，不列为 fact |
| 用户未确认就补 Acceptance | 停在 Story Review Gate |
