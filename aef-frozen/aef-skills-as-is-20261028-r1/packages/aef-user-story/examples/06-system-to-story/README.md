# 整体层级对话示例（合成）

这是方法示范，不是真实项目需求或批准。

## 个人支持产品

用户：“定义已经明确，我要先设计一个能用的系统。用户有基本资料，绑定一个支持系统，里面有任务和方法。”

合适的首轮：
- 组成候选：使用者基本描述、可配置的支持系统、双方绑定关系、系统内的任务与可调用方法。
- 关系候选：使用者通过绑定关系使用一个系统；任务和方法属于或可被系统调用。能否多系统、谁配置、是否生成均未知。
- 粗能力：建立基本描述；准备可用系统；建立绑定；通过任务和方法获得支持。每项先概括为Epic或粗故事。
- 候选闭环：建立描述→准备系统→绑定→完成一次系统内任务。只是讨论骨架，尚未冻结MVP。
- 当前主问题：“第一个版本里的系统，主要由产品方预先设计、由用户配置，还是需要AI生成？这会改变我们要交付的配置能力。”

不合适的首轮：直接列出35条中断/恢复/求助细节，再要求描述最近一次困难。
心理支持、主动性、记忆和游戏化可以成为约束或跨能力要求；它们不能自动替代上面的对象与关系。

后续用户明确“首版使用产品方预设系统，用户填写自己的描述并选择绑定”后，才能收敛配置责任；不因选择预设就删除远期其他配置方式。
先比较首个闭环，再选中“绑定预设系统”细化完整故事，Story确认后讨论编号验收；未选能力保持概括。
若用户只要求调整一条验收，则直接读取该卡局部处理，不重做上述讨论。

## 培训报名产品

用户：“产品定义定了，先看看首版整体怎么做。”

首轮应围绕课程供给、可报名班期、报名者与报名关系、参与资格等业务组成，解释“发布班期→选择报名→取得资格→参与”的流程。
是否收费、谁审核、取消规则保留未知；不要照搬“宿主绑定系统”，也不要直接设计支付API。
先确定首版闭环，再细化选中故事。不因为例子里有费用就决定收费方式。
