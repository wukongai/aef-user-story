# AEF User Story 用户操作手册

这份手册不要求你懂敏捷开发，也不要求你先会写 User Story。

你只需要把真实想法告诉 Agent。`aef-user-story` 会陪你把模糊需求改成可确认的 User Story，补齐可检查的验收条件，再保存进项目。

Skill 地址：<https://github.com/wukongai/aef-user-story>

## 你最终会得到什么

默认情况下，一个需求会落到项目里的两个文件：

```text
docs/requirements/<slug>/
├── user-story.md
└── story-card.json
```

- `user-story.md`：给你和团队阅读、讨论和评审。
- `story-card.json`：给 Agent 和后续工具读取，避免换一次对话就丢掉确认结果。

它们会记录：Epic、User Story、INVEST 检查、验收条件、用户确认和下一步去向。

## 开始前，你需要准备什么

- 一个支持目录型 Skill 的编程 Agent，例如 Codex 或 Claude Code。
- 一个准备开发的项目目录。
- 一句真实需求。哪怕它现在很模糊，也可以开始。

第一次使用，建议选一个小需求跑完整流程。先看见两个文件真正写进项目，再处理复杂需求。

## 第一步：把 Skill 交给 Agent

打开你的编程 Agent，进入准备开发的项目。

你可以直接对 Agent 说：

```text
请从这个仓库安装 aef-user-story Skill：
https://github.com/wukongai/aef-user-story

安装到当前项目，并告诉我安装到了哪里。先不要处理需求。
```

也可以自己运行：

```bash
npx skills add wukongai/aef-user-story
```

安装器询问安装范围时，第一次试用建议选择“当前项目”，这样不会影响其他项目。

### Agent 会做什么

Agent 会读取 Skill，完成项目级安装，并告诉你安装位置。不同 Agent 的目录可能不同，这是正常的。

### 你要检查什么

- Agent 是否明确说安装成功。
- 安装目标是否是你当前打开的项目。
- Agent 是否能读到 Skill 的中文说明。

如果 Agent 没有识别到 Skill，可以重新打开一个任务或会话，再继续第二步。

## 第二步：说出一句模糊需求

不要先替 Agent 写标准格式，也不要为了“显得专业”补充并不存在的细节。像平时说需求一样说出来就行。

下面先用一个最小案例跑通：用户点击逐字稿，可以回到视频对应的位置。

你可以直接对 Agent 说：

```text
请使用 aef-user-story 帮我整理这个需求：
我想让用户点一下视频转出来的文字，就能跳回视频那里。
```

### Agent 会做什么

Agent 不会立刻写代码。它会先：

1. 用直白的话复述你真正想解决的问题。
2. 区分已经确定的事实、暂时假设和还不知道的内容。
3. 询问少量会改变 Story 边界的问题。
4. 给出候选 Epic 和 User Story。

例如，Agent 可能会问：

> 主要是谁在使用？普通“视频用户”，还是带着学习、回看目的的人？

你可以回答：

```text
是看课程和访谈的学习者，“视频学习者”更准确。
```

### 你要检查什么

- Agent 有没有先理解需求，而不是直接进入技术方案。
- 它有没有把“不知道的内容”诚实标出来。
- 它问的问题是否真的会影响用户、目标或边界。
- 它有没有擅自加入搜索、摘要、笔记等你没提过的功能。

## 第三步：修改并确认 User Story

Agent 会给出类似这样的候选 Story：

> 作为视频学习者，我希望点击逐字稿片段后，视频跳转到对应时间，以便快速回看相关内容。

这不是最终答案。你可以像修改普通文案一样继续改它。

你可以直接对 Agent 说：

```text
角色用“视频学习者”，不要用笼统的“视频用户”。
这一条只保留“点击逐字稿跳回对应时间”，暂时不要加入搜索、摘要和笔记。
请修改后重新给我检查。
```

Agent 还会用 INVEST 检查这条 Story：

- **I — Independent**：是否能作为一个相对独立的结果讨论。
- **N — Negotiable**：是否描述目标，而不是提前锁死技术做法。
- **V — Valuable**：是否给明确用户带来可说明的价值。
- **E — Estimable**：信息是否足够进入下一阶段判断复杂度。
- **S — Small**：是否只包含一个足够小的用户结果。
- **T — Testable**：是否能写出可观察的验收条件。

你不需要背这六个英文单词。重点是让 Agent 告诉你：为什么这条 Story 足够清楚，哪里仍然有风险。

修改满意后，你可以直接对 Agent 说：

```text
确认 User Story，就按当前这版继续补验收条件。
```

### Agent 会做什么

Agent 会记录这次明确确认。只有确认后的 Story 才会继续生成验收条件。

### 你要检查什么

- 角色是不是具体的真实用户。
- Story 是否只保留一个用户结果。
- 价值是否说清“为什么需要它”。
- INVEST 的每一项是否有针对当前 Story 的理由，而不是只写“通过”。
- 你是否真的说了“确认”，而不是仅仅说“看起来还行”。

## 第四步：修改并确认验收条件

验收条件回答的不是“程序怎么写”，而是“做到什么现象才算交付”。

每条已确认 Story 至少要覆盖三类条件：

- `success`：正常情况下，用户能观察到什么结果。
- `failure`：操作失败时，系统怎样避免造成错误或丢失。
- `boundary`：缺数据、无权限、空内容等边界情况怎么处理。

在这个案例中，Agent 可能先写：

- success：点击带时间信息的逐字稿片段，视频跳到对应位置并继续播放。
- failure：跳转失败时保留当前位置，并提示用户重试。
- boundary：逐字稿没有时间信息时，不发生错误跳转并提示无法定位。

如果你发现“不发生跳转”还不够，可以继续补充：

你可以直接对 Agent 说：

```text
修改 boundary：逐字稿没有时间信息时，除了不错误跳转和提示原因，还要给用户一个重新解析的入口。
修改后把三类验收条件重新展示给我。
```

满意后，你可以直接对 Agent 说：

```text
确认验收条件，按当前版本进入写入预览。
```

### Agent 会做什么

Agent 会重新检查 success、failure、boundary 是否都能观察和验证，并记录第二次确认。

### 你要检查什么

- 条件描述的是外部可见结果，不是函数名、数据库表或框架选型。
- 成功、失败和边界三种情况是否都覆盖。
- 是否明确什么不能发生，例如“不得跳到错误时间”。
- 修改 Story 后，Agent 是否让旧验收条件失效并重新确认。

## 第五步：批准写入项目

两次确认结束后，Agent 仍然不能直接写文件。它必须先告诉你准备写到哪里、写几个文件、是否会覆盖已有内容。

你应该看到类似预览：

```text
docs/requirements/video-transcript-jump/
├── user-story.md
└── story-card.json
```

预览还应说明：

- 本次包含 1 条已批准 Story。
- 包含 3 类验收条件。
- 两个文件是新建还是更新。
- 不会顺手生成 PRD、Spec、Task 或代码。

如果路径和范围都正确，你可以直接对 Agent 说：

```text
批准写入，按预览路径生成 user-story.md 和 story-card.json。
```

### Agent 会做什么

Agent 会把人读文档和机器合同一起写入项目，并检查两份文件中的 Story ID、验收条件 ID 和确认状态是否一致。

### 你要检查什么

- 路径是不是当前项目，而不是其他仓库。
- 是否只写了预览中的两个文件。
- 已有文件是否被提前说明，Agent 有没有静默覆盖。
- `user-story.md` 和 `story-card.json` 是否表达同一组 Story 和验收条件。

你也可以让 Agent 做确定性检查：

```text
请运行 aef-user-story 自带的 package 校验器，检查刚生成的目录，并把检查结果用中文告诉我。
```

## 第六步：选择下一步

User Story 写清楚后，不一定必须先写 PRD。

每条已批准 Story 会选择一个下一步：

- `direct_spec`：边界已清楚，直接进入开发 Spec。
- `prd`：多条 Story 之间还有统一流程、规则或业务关系要补。
- `backlog`：这次明确不做，但保留原因。
- `specialist_review`：先进入法律、安全、隐私或合规等专项评审。

对于“点击逐字稿跳回视频”这个单一需求，通常可以直接进入 Spec。

你可以直接对 Agent 说：

```text
请解释这条 Story 为什么适合 direct_spec。
只给出交接摘要和目标 Spec ID，不要在这个 Skill 里代写 Spec。
```

如果是一组共享业务流程的 Story，可以说：

```text
请判断这些 Story 是否需要先补 PRD。
PRD 不是必选项：只有存在跨 Story 的统一流程或规则时才选择 prd，并说明原因。
```

### Agent 会做什么

Agent 会为每条已批准 Story 记录一个明确去向，但 `aef-user-story` 到这里就停止，不会越界生成后续文档。

### 你要检查什么

- 是否每条已批准 Story 恰好有一个下一步。
- Agent 是否把 PRD 当成可选项，而不是固定步骤。
- 进入 Spec 时，是否还能用 Story ID 和 Acceptance ID 追踪回来。

## 第七步：换成你自己的需求

跑通示例后，直接换成真实项目需求。你不需要自己判断它是一条 Story 还是一个 Epic。

你可以直接对 Agent 说：

```text
请使用 aef-user-story 处理下面这个真实需求。

先复述和澄清，再给候选 Story；允许我逐条修改。
我明确确认 User Story 后才能补验收条件；我再次确认验收条件后，先预览写入路径，等我批准再写文件。

我的需求是：
【把你的原话粘贴在这里】
```

### Agent 会做什么

无论输入是一句话、功能清单，还是一条看似标准但过大的 Story，Agent 都会先判断需求结构，再带你完成修改和确认。

### 你要检查什么

- Agent 是否保留了你的真实目标，没有为了格式漂亮改变需求。
- 不确定项是否仍被标记为未知，而不是被 Agent 猜成事实。
- 每一次确认是否发生在你看到完整内容之后。
- 最终文件是否能成为后续 PRD 或 Spec 的输入。

## 三个完整案例

下面三个案例分别对应最常见的三种输入。完整对话和最终文件也保存在仓库的 `examples/` 目录中。

### 案例一：一句模糊需求变成一条 Story

用户原话：

```text
我想让用户点一下视频转出来的文字，就能跳回视频那里。
```

关键互动：

1. Agent 询问真实用户，用户把“视频用户”改成“视频学习者”。
2. 用户明确本次只做逐字稿定位，不增加搜索、摘要和笔记。
3. User Story 确认后，Agent 才补验收条件。
4. 用户要求无时间信息时增加“重新解析”入口。
5. 验收条件确认后，用户批准写入。

最终结果：

- 1 条 approved Story。
- success、failure、boundary 各 1 条。
- 写入 `docs/requirements/video-transcript-jump/`。
- 下一步为 `direct_spec`。

完整材料：[案例一完整对话](../../examples/01-video-transcript-jump/conversation.md)

### 案例二：一堆功能拆成 Epic 和多条 Story

用户原话：

```text
做个 AI 会议助手，要录音、转写、总结、自动分配任务、搜索历史会议、分享，还要权限。
```

关键互动：

1. Agent 识别这不是一条 Story，而是一个混合多个结果的 Epic。
2. 用户说明首版目标是“团队拿到准确纪要和待办”。
3. “自动分配任务”被改成“AI 提议，组织者确认后发布”，避免 AI 直接影响成员。
4. 六条候选 Story 中，三条 approved，三条 deferred 并保留原因。
5. 三条首版 Story 共享同一业务流程，因此先进入一个 `prd`。

你可以直接对 Agent 说：

```text
不要把这串功能硬塞进一条 User Story。
请先识别 Epic，再按独立用户结果拆成候选 Story；让我决定哪些进入首版、哪些进入 backlog。
```

最终结果：

- 1 个 Epic，6 条候选 Story。
- 3 条 approved，3 条 deferred。
- 已批准 Story 共 9 条验收条件。
- 写入 `docs/requirements/ai-meeting-assistant/`。
- 下一步为 `prd`，用来补统一的会议结束、摘要和任务确认流程。

完整材料：[案例二完整对话](../../examples/02-ai-meeting-assistant/conversation.md)

### 案例三：一句完整但过大的 Story 重新拆分

用户原话：

```text
作为自媒体作者，我希望 AI 帮我找选题、写文章、配图、审核并发布，这样我可以全自动做内容。
```

它看起来有标准句式，但一次包含五个结果，“全自动”还提前锁定了解法。INVEST 中的独立性、可评估性、小型化和可测试性都会出问题。

关键互动：

1. Agent 把它识别成 Epic，而不是因为句式正确就放行。
2. 先拆出选题、写作、配图、审核、发布五条候选 Story。
3. 用户说明没有独立审核者，于是删除虚构的“审核 Story”。
4. “作者发布前确认内容与素材”被放进发布 Story 的验收条件。
5. 四条 Story 可以独立进入各自的 Spec，不在 User Story 阶段拆开发 Task。

你可以直接对 Agent 说：

```text
请不要只检查句式，要用 INVEST 判断这条 Story 是否过大。
如果包含多个独立用户结果，先说明哪些项不通过，再拆成可分别确认的 Story。
```

最终结果：

- 4 条 approved Story。
- 每条 Story 都有 success、failure、boundary。
- 写入 `docs/requirements/ai-content-workflow/`。
- 四条 Story 分别进入 `direct_spec`。

完整材料：[案例三完整对话](../../examples/03-ai-content-workflow/conversation.md)

## 常见问题

### 我必须先学会 User Story 才能使用吗？

不需要。你负责说明真实目标、纠正 Agent 和做确认；Skill 负责提供结构、检查 INVEST 和保存结果。

### 一条需求一定只生成一条 Story 吗？

不一定。一句话可能是一条小 Story，也可能包含一个 Epic。关键看它包含多少个独立用户结果，不看句子长短。

### User Story 后面一定要写 PRD 吗？

不一定。单条 Story 边界清楚时可以直接进入 Spec；多条 Story 还有统一业务流程或规则时，再选择 PRD。

### 为什么要确认三次？

三次确认保护的是三个不同对象：

1. 确认 User Story：需求边界对了。
2. 确认验收条件：怎样算完成对了。
3. 批准写入：文件路径和实际改动对了。

前一次确认不能替代后一次确认。

### Story 要在这里估算工作量吗？

当前版本不做 Story Point 或开发量估算。可靠估算通常还依赖技术方案和项目现状，放到后续 Spec 或计划阶段更合适。

### 它会直接帮我写代码吗？

不会。本 Skill 的边界是把需求和验收条件写清楚，并提供到 PRD、Spec、backlog 或专项评审的钩子。

## 使用时不要这样做

- 不要让 Agent 第一次看到需求就直接写代码。
- 不要把“有标准句式”误认为 Story 已经足够小。
- 不要接受只有“正常成功”的验收条件。
- 不要用“嗯”“差不多”代替明确确认。
- 不要在没看路径时批准写入。
- 不要把 PRD 当成所有 Story 的固定下一步。
- 不要在 User Story 阶段提前拆开发 Task；Task 的垂直切片应放在后续开发规划阶段处理。

## 当前边界

`aef-user-story` 负责需求澄清、Epic/Story 拆分、INVEST 检查、验收条件、三次确认、双文件落盘和下游路由。

它不生成正式 PRD、技术 Spec、架构、UI 设计、开发计划、开发 Task、测试代码或业务代码。

如果运行环境没有 Python，Agent 仍可生成文档，但必须明确说明没有执行 JSON 和双文件一致性校验。

## 遇到问题怎么反馈

反馈时请尽量带上：

- 你给 Agent 的原始需求。
- Agent 从哪一步开始偏离预期。
- 生成的 `user-story.md` 和 `story-card.json`（先移除敏感业务信息）。
- 使用的 Agent 名称和 Skill 版本。

可以在仓库提交 Issue：<https://github.com/wukongai/aef-user-story/issues>
