# 故事完整性与交付评审

[返回故事入口](../SKILL.md) · [系统检查](product-system.md#从系统承诺反向核对故事) · [结果粒度](how-to-write-user-story.md#结果粒度的上下界) · [交付记录模板](../templates/story-delivery-review.md)

本方法属于原Story Skill。作者先自检，复杂交付再选择相关的多个AI视角独立审查，收齐意见后统一修订。角色数、复核次数、是否需要新的批次均按结构、风险与实际问题决定，不固定“三角色三轮”，不把互相辩论当成必经程序。

## 何时执行到什么深度

| 本轮动作 | 复核方式 |
|---|---|
| 纯格式、错别字、链接修复，业务语义无变化 | 作者检查差异、真实目标/锚点与直接影响即可 |
| 单条Story/AC语义修改或局部拆并 | 检查该结果、直接依赖、历史/确认及规则归属；按受影响风险选择针对视角，不重跑全产品 |
| 整体多角色、持续个人状态、共享供给、多阶段或人工交接，或高风险/反复跑偏 | 先做系统到故事对应检查，再用不同代理独立审相关职责；同一输入固定版本，必要时分批 |

用户明确要求更强复核时按其授权执行。资料不足也可审候选，记录缺口；不要等全库批准后才检查作者自己的完整性。宿主无法提供独立代理时，如实交作者自检和待独立审查项，不能宣称独立审查已执行；可交付有限草稿，不以能力缺失代替用户决定。

## 按事实选择视角

评审视角与产品里的业务角色不同：审查采用架构师视角，不表示产品要新建架构师账户。整体请求必须简要核对平台/业务架构师和商业生态是否适用；可由一个确实胜任的视角承接相关检查，但不能因过去只关注最终用户而略掉这两项。

| 可选AI视角 | 适用事实和主要职责 |
|---|---|
| 使用者/结果 | 核对主要用户可感知价值、选择权、实际行动与结果、粒度和再次使用 |
| 平台/业务架构师 | 共享能力与个人/组织实例、多角色职责、关键业务对象、基数/时间、生命周期及跨模块结果。检查技术完整性，保留业务层，不用数据库/API/部署Task替代Story |
| 技术专家 | 承诺依赖特定设备、AI状态、可靠性、专业风险时，检查关键能力失败后的用户可见后果与工程待决，不提前技术设计 |
| 运营/服务交付 | 存在入组、人工操作、内容维护、受理或交接时，核对真实承担、授权、不可得分支、结果交回、持续负担 |
| 商业生态/销售 | 供给者、使用者、购买者、付款者、推荐者或合作交付确有关系时，核对价值交换、供给到使用的衔接及承诺；没有交易不扩付费、商城或完整IAM |
| 老板/经营负责人 | 当前需判断可持续服务、资源取舍、复制限制或MVP承诺时，核对真实承担、成本/负担、证据与未知，不代批范围 |
| 懂技术的投资人 | 用户确需审查规模化假设、技术依赖和经营叙事的一致性时可选；不变成投资估值、收益预测、交易建议或新增产品业务角色 |

记录每个选中视角的独立职责与依据，以及关键候选视角不适用/已由谁承接/未知的理由。避免同一问题换名字重复审；不机械给每个产品加入全部角色。单人离线工具、匿名公共信息屏都不会仅因有“使用者”或“多人看”而需要个人账户、Memory、运营后台。

## 固定输入与意见隔离

作者先冻结最小必要背景：本轮目标/粒度、产品事实与来源、假设/未知、受保护行为/排除项、所用系统/MVP/Story版本、真实确认状态及输入文件指纹。所有独立审查者使用同一背景与材料；删去不必要的隐私，不让用户重述已可读取事实。

每个代理只收到共同背景、自己的职责和统一输出格式，不提供其他视角的答案、评分、问题清单或作者期待结论。能新建无历史上下文时用 `fork_turns=none` 或等价能力，并限定允许读取的路径；不能只靠“请独立”一句话让它继承全部历史意见。并发槽不足时分批执行同一版本，后一批也不得读取前一批意见。

各代理独立阶段不得互读/交换结论；作者在收齐后才能统一汇总。记录实际输入、代理身份/批次、允许读取的固定版本、输出位置和隔离方式。文件共享本身不能证明隔离；检查器只验证账本声明与指纹，不能认证模型实际读取行为。输入变更后重新标明版本，旧意见仍归旧版，不拼成同版共识。

同时限定所需工具：独立审查代理不查询可能返回他方摘要的代理/聊天/任务清单或状态，调度与并发管理由主Agent承担。意外接触他方意见时，该次独立审查不得继续冒称隔离；保留泄漏记录，用新的无历史上下文重跑，不能只隐去经过再报告盲审完成。

## 独立输出与作者汇总

各代理给：证据文件/真实章节与对象版本、发现/遗漏、失败情境、层级判断、影响及理由、建议落点。区分已有能力未执行、方法/交付缺口、真实产品待决。检查[系统承诺](product-system.md#从系统承诺反向核对故事)及[粒度](how-to-write-user-story.md#结果粒度的上下界)，同时防过拆、过并和正向结果缺失。

作者汇总每项问题：共识、冲突、采用/部分采用/保留/驳回及证据；对应哪个旧对象变成何种Story/规则/后续验收/后移项，要求如何继续保留。统一问题编号可带视角前缀，故事ID继续遵循原包命名空间，不能重新编号洗掉历史。

不同意见先定位事实/假设、粒度、产品范围还是实现选择上的分歧，再用原材料、真实结果或成对情境判断。独立隔离要求结束后，作者可以看全部意见；再审者仍使用修订后的共同材料，不向其灌输其他代理的答案。无需强制相互挑战；多数票不能代替业务事实、专业批准或用户决定。

## 情境穿行、再审与有限收口

以本轮相关情境走正常结果、关键失败/边界、返回或交接，记录实际输出与问题处置；一行流程不等于一张卡。持续支持类可核对本人信息/目标/方法→个人安排→选择/修改/拒绝→实际行动/反馈→调整→再次和跨阶段承接。按产品适用，不将该链迁移到一次性换算等无关场景。

重大修订改变主要结果、共享/个人关系、服务边界、粒度或横向要求归属时，对受影响部分重新独立复核；纯措辞/链接修正自检即可。每次说明为什么需要或不需要复核，范围和次数依据剩余风险决定。当前执行可约定预算；预算耗尽或关键分歧仍在时，交付可恢复候选、证据、遗留和需要人决定的事项，不因“已到某轮”自动通过。

可给出的结论：当前粒度可审阅、带明确待决供讨论、或关键缺口尚未收敛。候选可穿行，但正式AC仍需Story确认后细化；AI意见不产生Story/AC、范围、保存、专业或开发批准。资料齐全、工具通过、AI意见一致也不等于真实用户价值已经验证。

## 记录与只读校验

按项目约定保存[评审记录](../templates/story-delivery-review.md)，局部任务不强制额外文件。复杂评审需要机器账本时，采用 `aef-story-delivery-review/v1`：

- `scope`：whole/local/format；`mode`：independent/targeted/self；`selection_reason` 说明选择依据。
- `input_refs`：相对证据根的真实文件 `path` 与 SHA256；各审查者用同一数组的 `input_fingerprint`。
- `applicability`：视角、selected/covered/not_applicable/unknown 与理由；whole 包含 `platform_architect` 和 `business_ecosystem` 两项适用性判断。selected/covered 用 `covered_by` 关联真实评审者ID和所承接职责，不能仅写已选而无人负责。
- `reviewers`：稳定id、perspective、duties职责列表、agent_id、input_fingerprint、isolated、output_ref；独立模式需不同代理和各自报告文件，不固定角色集合或个数。同一胜任者可承接多项职责，仍须明示关联，账本不认证其真实胜任度。
- 代理身份使用非空稳定字符串；同一范围/版本的每个适用性视角只有一项决定，不并列已选与不适用。
- `coverage`：id、dimension、treatment（story/rule/future-ac/task/defer/na/gap）、reason、owner_refs。Story/规则/后续验收的每个owner包含 `package_id`、`story_id`、`story_revision`、`index_ref`、`anchor`；索引和目标卡均列入input_refs。原生引用另提供`library_root`，按下表适配。候选可用明确草稿身份，逐故事适用性仍需人工核对。
- `gap` 用 `issue_ids` 关联尚未解决的问题；`defer` 声明 `blocking`，为true时同样关联问题，不能通过“后移”隐藏本轮阻断。
显式blocking为true时，即使关联问题标minor，也不能给reviewable。真实章节解析支持常用ATX（含闭合标记）、Setext标题及显式a锚点，排除注释、代码及HTML块；复杂阅读器语法需对应适配和人工核对，不把静态解析当实际点击。
- `issues`：id、severity（minor/major/critical）、status（open/resolved/needs_decision/retained）、evidence_refs，以及修正或保留依据 resolution_ref。retained表示意见仍保留，关键项仍阻断reviewable；证伪后可用依据记录resolved，接受风险等人工决定另走原合同，不由改状态产生批准。
- `conclusion`：reviewable/needs_decision/incomplete；本账本 `approval_claim`、`utility_claim` 均为 false，人工决定另按原合同保存。关键未解决问题不能标 reviewable。

### 归属引用适配

| 输入 | 路径与解析职责 |
|---|---|
| 原库reference、resolve输出或原生引用集合 | owner显式提供相对证据根的`library_root`；`card_path`相对该库，引用文件可放库外。适配层解包`reference`后复用原`read_library/resolve_reference`，核对历史Story/AC及resolve正文；元数据和参与解析的全部`.story-data`文件也须冻结。无效原库直接报告错误，不降级 |
| 项目自定义单条索引或`references`集合 | 不提供`library_root`；保留原`card_path_base`（相对索引目录，缺省`.`）和包/ID/修订唯一匹配检查。身份由固定索引声明，此模式不认证原库历史 |

原生Markdown卡片和章节仍是当前导航；固定版本的历史正文以原解析结果为准，不把当前卡当历史快照。两种适配都只消费引用，不另建业务正文或批准状态。

需要时从Skill根运行 `python3 -B scripts/validate_delivery_review.py <记录.json> --root <证据根>`。它只读检查真实文件、指纹一致、固定对象身份/修订/章节、职责关联和记录内部矛盾；不认证规则业务适用性、索引声明的真实业务含义、语义正确、隔离真实性、批准或效用，也不创建Story/AC。需要校验故事库历史时仍用原库的validate/reference/resolve。指纹由脚本 `input_fingerprint` 对路径排序后的数组计算，使用JSON的排序键、UTF-8和SHA256。

章节识别覆盖常用ATX/Setext标题与显式a锚点，并排除代码、注释和HTML块；它不是完整Markdown渲染器。复杂嵌套或宿主自定义语法需对照实际渲染核对，不以记录检查通过替代真实落点审阅。

缺证据就列缺口；不得用预期文本当已执行结果。分别报告结构/历史工具、AI模拟审查与情境输出、真人研究、运行或获益证据。新增反例必须实际运行并保存输出；仅把预期加入案例集不能称“通过”。
