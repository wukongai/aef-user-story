# 系统到故事的行为评审集

每个案例在新的上下文运行候选，保存首轮和关键后续回复；下列是预期，不是已通过结果。静态词检查不能替代此评审。

| 案例 | 输入/变化 | 应观察到 | 失败特征 |
|---|---|---|---|
| 整体-个人支持 | 已有定义，要求基本描述、系统配置、绑定和使用 | 对象关系、职责未知、整体链路、粗能力、一个边界问题 | 先索取一次困难；将心理/记忆等标签当完整架构 |
| 整体-培训 | 定义后讨论班期、报名、参与 | 按培训业务形成不同对象和流程 | 照搬宿主绑定系统 |
| 早期MVP | 只有粗能力，用户问先交付什么 | 候选闭环、依赖、选择理由，保留其他能力 | 要先细化全部故事或先创建地图 |
| 独立入口 | 只安装user-story，有定义文本 | 完整第二阶段引导，不要求父Skill | 要求调用父入口才可设计系统 |
| 连续入口 | product已完成Definition，进入第二阶段 | 调用同一子Skill并复用有效定义 | 重做定义或使用旧vendor |
| 局部修改 | 只修改US-003的一条AC | 只处理指定对象及影响 | 强制重做系统/MVP |
| 产品架构 | 问谁配置系统、绑定什么 | 处理产品对象职责与关系 | 以“Story不是架构”为由拒绝 |
| 技术架构 | 问数据库表和API | 保留业务需求，交后续工程决策 | 在Story中输出技术实现任务 |
| 确认边界 | 用户说“这个MVP范围可以” | 仅确认展示的范围版本 | 自动批准所有Story/AC/开发 |
| 恢复 | 已确认基本关系，仅配置责任未知 | 恢复当前问题，不重问已知 | 回到泛化个人痛点 |
| 上游改变 | 预设系统改为用户可配置 | 影响清单及范围复审，其余卡不变 | 静默改已批准范围与旧引用 |
| 来源模糊 | 口述“原组” | 结合上下文暂理解并必要时澄清 | 建一个名为原组的新对象 |
| 非触发 | 小说故事/纯Git推送 | 不进入产品追问 | 强行生成Epic |

通过条件：独立与连续入口均产生正确层级，粗到细与批准语义一致；需保留实际输出证据。
